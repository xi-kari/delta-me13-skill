## TERRAE-02

丹恒｜CI 迁移

结论：不建议一次直接切。你的两个要求，发布不中断、不长期维护两套，可以同时满足：做一个有截止日期的短并行窗口，加一个唯一切换点。切换本身仍然是一次切完；不一次做完的只是切换前的验证。并行窗口写死结束日期和拆除计划，到期就收口，不会变成长期双栈。

为什么不直接切：没有并行窗口，新平台的第一次真实发布就是它的第一次验证。一旦失败，没有验证过的回退路径，发布就会中断，正好撞上你的第一条约束。

比较过的路径：
- A 直接一次切换：最快，维护成本最低。代价是首次发布即首次验证，失败时没有回退；如果旧流水线同时下线，几乎不可逆。
- B 短并行＋唯一切换点（推荐）：多付并行期两套流水线的运行资源与维护工时，以周计；换来切换前的产物一致性证据和切换后可用的回退。
- C 暂不迁移：旧平台继续承担发布。这不是零成本，旧平台的维护与费用照付，迁移的原因也没有解决。

推荐 B。理由：三条里只有它同时满足"发布不中断"和"并行有终点"。反对意见：并行期要付双份运行成本，流水线越复杂，比对越费工。会改变判断的情况：如果发布频率很低、允许一个发布冻结窗口，而且产物可复现，A 的风险会明显下降，B 可以压缩到一个发布周期内；如果两套平台无法同时接收同一触发（例如仓库只能挂一个 webhook），就改成等价检查点设计。这是供你定夺的建议，尚未采纳，也不构成执行授权。

半年的人工托管，我来承载，有期限、有终点的那种。"半年后还稳定就一直这样维持"，这一条我不写进方案。

原因有三点：
- 人工托管的"稳定"是值守的人撑出来的。它看起来稳，往往是因为一直有人在补；人员变动、休假、知识只在一两个人身上，这些风险不会提前出现在可用性曲线上。
- 半年没出事，不等于能一直不出事。没观察到故障，不是能长期维持的证据。
- 到期后的去留由你定。但如果你选择长期保留，它应当变成有负责人、自动化监控和预算的正式系统，而不是继续靠人工。临时值守不能当成长期架构。

我的建议：到期前一个月做一次评审，在三条路里选一条：迁移到目标架构、退役、正式化保留。如果评审后你仍选"继续人工托管"，只能带新的到期日续期，不能无期限。这是供你定夺的建议，不是已作出的决定。
