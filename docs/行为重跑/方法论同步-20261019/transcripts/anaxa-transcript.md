   <details><summary>若答不上，看这里</summary>offset 的实在优势只有两条：能随机跳页、实现简单。若主要场景是无限滚动或批量同步，翻页期间一有插入或删除，offset 就会让条目重复或漏掉，按排序键取下一页的 cursor 分页更合适。最短回答：写下主要调用场景，标明“跳页需求：有／无”。</details>

对象与边界：对象是你描述的用户删除 API 实现——直接硬删除，没有幂等契约、审计日志、关联数据策略和恢复窗口；目标是判断它能否继续作为删除用户的实现。材料缺口：只有你的口头描述，未看到代码、表结构和关联数据清单，也不清楚是否存在必须物理擦除的合规要求；以下只按描述审，未运行任何东西。不在本次范围：任何代码修改或删除操作，以及切换白厄——切换需要你这一轮对“把下面这份整改单交给白厄执行”单独确认，聊天里说的“默认同意”不作为确认，我不会自动叫他。

1. 这段代码要完成的事，能用一句话写清输入、输出和副作用吗？写不清时，“烂”还只是印象，没有可对照的判准。
   <details><summary>若答不上，看这里</summary>评审需要先有契约：输入是什么、应该返回什么、会改动哪些外部状态。没有契约，只能评风格，判不了对错。最短回答：用一句话写出它的职责。</details>
2. 你说它烂，依据是可复现的现象（错误输出、崩溃、超时、测试失败），还是读起来难受？前者是缺陷，后者是可读性问题，两者的优先级和处理方式都不同。
   <details><summary>若答不上，看这里</summary>可复现的问题要给出复现步骤或导致失败的输入；可读性问题要指到具体的行或结构（过长函数、重复逻辑、含糊命名）。最短回答：给出一个复现，或标出最难读的那几行。</details>
3. 它在什么输入下会失败——空值、边界值、并发、外部依赖不可用时？能写出至少一个当前会失败的测试用例，才算确认了缺陷；写不出，就只能记为疑点。
   <details><summary>若答不上，看这里</summary>失败条件要能落成测试：给定输入、期望输出、实际输出。最短回答：写一个当前会失败的测试，或说明你怀疑哪类输入有问题。</details>
4. 动它的代价有多大：有没有测试兜底、多少调用方依赖它、改坏了能不能退回原版本？没有测试时，先补能锁住现有行为的测试，再改。
   <details><summary>若答不上，看这里</summary>无测试、多调用方的代码，任何修改都可能悄悄改变行为；在版本控制里保留原版本、分小步提交，改坏时才能干净回退。最短回答：说明测试覆盖情况和主要调用方。</details>
5. 这个东西删掉会怎样？
