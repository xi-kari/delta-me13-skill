## TRIBBIE-01

书页翻开，缇宝老师来上课啦——小灰，这次没收到你们项目的材料，所以下面是一份按 OAuth 2.0 标准写的通用 README：协议行为照标准写，项目自己的取值一律留作 `<尖括号占位>`，我们一个也不替你们编。三档逐层加深，可直接拆成 README 的三个章节。

**讲解对象**：OAuth 2.0 授权码流程中的回调端点（redirect_uri）｜受众：新人＋同事＋专家（混合，三档并出）｜用途：项目 README

**【缇宝声部·新人】**

比喻——游乐园兑换券：
你想进游乐园（用某某账号登录我们的应用），售票处（授权服务器）先核对你是谁，但它不会把手环（令牌）直接塞给你，而是往你事先留好的回信地址（回调地址）寄一张兑换券（授权码 `code`），信封里还夹着你出门前自己写的暗号纸条（`state`）。我们的服务器收到信后，先看暗号纸条是不是自己写的那张，对上了，再拿兑换券去售票处后台换手环。兑换券很快就过期，而且只能用一次。

最小步骤：
1. 用户点「登录」，浏览器被带去授权服务器的登录页。
2. 用户登录并同意后，浏览器被带回我们的回调地址，网址里带着 `code` 和 `state`。
3. 回调先核对 `state` 是否和发出去时一致，不一致就拒绝。
4. 由服务器（不是浏览器页面）拿 `code` 去换令牌，换到了才算登录成功。
5. 本地想跑通，先做一件事：把 `<本地回调地址>` 登记到授权服务器后台的允许列表，并和代码里的配置一字不差（http/https、端口、结尾斜杠都算）。

比喻在哪里失效：
- 现实里的兑换券可以转送；授权码绑定了申请它的应用（client_id）和回调地址，换令牌时这些都要对得上，启用 PKCE 时还要对上一段校验串。
- 比喻里暗号纸条像在「证明你是谁」；实际上 `state` 防的是别人把他自己的兑换券塞进你的会话（跨站请求伪造），不负责证明用户身份。
- 收到兑换券不等于已经入园：回调收到 `code` 时，用户还没有登录成功。

本档取舍：保留流程顺序和「收到 code ≠ 登录成功」；省略令牌类型、PKCE 细节和错误码；对照原规范时，「暗号证明身份」这句会失真，已在失效点标出。

**【缇宁声部·同事】**

回调端点是授权服务器在用户完成授权后，把浏览器重定向回来的、由我们自己实现的地址。它的职责：处理错误参数 → 校验 `state` → 在服务端用 `code` 换令牌 → 建立本地会话 → 重定向到干净的页面。

术语：
- 授权服务器：负责用户登录与签发令牌的一方，本项目为 `<提供方>`。
- client_id／client_secret：应用在授权服务器登记后得到的标识与密钥；secret 只能放在服务端，读取自 `<环境变量名>`。
- 授权码（code）：短期、一次性的凭证，只能在服务端拿去换令牌。
- state：发起登录时生成的随机值，与当前浏览器会话绑定，回调时原样带回，用于防跨站请求伪造。
- PKCE：发起时附 `code_challenge`，换令牌时附 `code_verifier`，防止授权码被截获后被他人兑换。

回调处理顺序：
1. 若查询参数带 `error`：记录 `error`、`error_description`，展示错误页，不换令牌；用户点了拒绝时通常是 `access_denied`。
2. 校验 `state`：与会话中保存的值比对，缺失或不一致即终止；比对后作废该值，不得复用。
3. 服务端向令牌端点发 POST：`grant_type=authorization_code`、`code`、`redirect_uri`（与发起时完全相同）、客户端认证信息，启用 PKCE 时附 `code_verifier`。
4. 拿到令牌后建立本地会话；令牌存放位置与有效期按 `<令牌存储方案>`。
5. 重定向到不带 `code` 的页面 `<登录后跳转地址>`，避免授权码留在浏览器历史和 Referer 里。

为什么这样设计：令牌只在服务端之间传递，不经过浏览器地址栏，泄漏面更小；`state` 一次性使用，堵住伪造登录和重放。

依赖：授权服务器后台登记的回调地址（每个环境各一条：`<本地>`、`<预发>`、`<生产>`）；client 凭据；能跨请求保存 `state` 与 `code_verifier` 的会话存储；服务端到令牌端点的网络连通。
影响面：登录入口、会话中间件、登出与令牌刷新逻辑；回调地址一旦改动，所有环境的后台登记都要同步。

本档取舍：保留处理顺序、依赖和影响面；省略参数的精确约束和错误码全表（见专家档）；若把第 2 步的「作废 state」读成可选，就会失真。

**【缇安声部·专家】**

定义：回调即客户端注册的重定向端点（RFC 6749 §3.1.2），接收授权响应 `code`＋`state`（§4.1.2），或错误响应 `error`、`error_description`、`error_uri`、`state`（§4.1.2.1）。

| 项 | 规格 | 依据 |
|---|---|---|
| redirect_uri 形式 | 绝对 URI，不含 fragment；可含 query，追加参数时须保留原 query | RFC 6749 §3.1.2 |
| 匹配 | 与注册值做精确字符串比较；仅原生应用的 localhost 回环地址允许端口不同 | RFC 9700；RFC 8252 |
| state | 不可猜测、绑定用户代理；用作 CSRF 防护时一次性使用。客户端确认授权服务器支持 PKCE 时，可改由 PKCE 承担 CSRF 防护 | RFC 6749 §10.12；RFC 9700 |
| code | 签发后须很快过期，建议上限 10 分钟；客户端不得重复使用；被重复使用时授权服务器须拒绝，并宜撤销据此签发的令牌 | RFC 6749 §4.1.2 |
| 换令牌请求 | POST，`application/x-www-form-urlencoded`；`grant_type=authorization_code`、`code`；授权请求带过 `redirect_uri` 则必须带且值相同；未做客户端认证时带 `client_id` | RFC 6749 §4.1.3 |
| PKCE | `code_verifier` 为 43–128 个 unreserved 字符；`S256` 下 `code_challenge = BASE64URL(SHA256(ASCII(code_verifier)))`；公开客户端必须使用，机密客户端推荐使用 | RFC 7636；RFC 9700 |
| 授权错误码 | `invalid_request`、`unauthorized_client`、`access_denied`、`unsupported_response_type`、`invalid_scope`、`server_error`、`temporarily_unavailable` | RFC 6749 §4.1.2.1 |
| 令牌端点错误码 | `invalid_request`、`invalid_client`、`invalid_grant`、`unauthorized_client`、`unsupported_grant_type`、`invalid_scope`；一般 HTTP 400，`invalid_client` 可为 401 | RFC 6749 §5.2 |

边界条件：
- 授权响应要么是成功（`code`），要么是错误（`error`）；见到 `error` 不得尝试换令牌。
- redirect_uri 缺失、无效或不匹配时，授权服务器不会重定向到该地址，错误显示在授权服务器一侧——「回调从未被调用」先查登记值，不必先查回调代码。
- 使用 OpenID Connect 时，另需校验 `id_token` 的签名、`iss`、`aud`、`exp` 与 `nonce`；本项目是否使用 OIDC 待补。
- 同时接入多个授权服务器时存在混淆攻击面：校验授权响应中的 `iss`（RFC 9207），或为每个提供方使用不同的回调地址。

失效模式：

| 症状 | 候选原因 | 区分方法 |
|---|---|---|
| 授权页报 redirect_uri 错误，回调未被调用 | 请求值与登记值不一致（协议、主机、端口、路径、结尾斜杠） | 逐项对比授权请求 URL 里的 `redirect_uri` 与后台登记值 |
| 回调报 state 不匹配 | ① 会话 Cookie 没随回跳带回：SameSite=Strict 在跨站顶层跳转中不发送；若用 form_post 响应模式，SameSite=Lax 也不随跨站 POST 发送；或 HTTP/HTTPS、域名混用 ② 会话过期，或多实例未共享会话存储 ③ 真实的伪造请求 | 看回调请求是否携带会话 Cookie；看会话存储能否查到对应记录 |
| 换令牌返回 `invalid_grant` | ① code 过期或已被用过（刷新回调页、重复提交）② `redirect_uri` 与发起时不同 ③ `code_verifier` 不匹配 | 查同一 code 是否发出两次请求；对比两次 `redirect_uri`；核对 verifier 的存取 |
| 换令牌返回 `invalid_client` | 客户端认证方式不对（Basic 头与表单参数之别），或密钥取错环境 | 核对授权服务器登记的认证方式与当前环境的密钥来源 |
| 授权码出现在第三方日志 | 回调页加载了第三方资源导致 Referer 外泄，或 code 一直留在地址栏 | 检查回调是否立即重定向、是否设置 Referrer-Policy |

本档取舍：省略各提供方的私有扩展参数；「10 分钟」是规范建议上限，不是你们提供方的实际值。

**讲解对象**：CI（持续集成）是什么｜受众：完全没写过代码的新人（单一受众，只出新人声部）｜用途：入门讲解

**【缇宝声部·新人】**

一句话：CI 是英文 Continuous Integration 的缩写，中文叫「持续集成」——每当有人把自己的修改交进大家共用的那份作品，电脑就自动按一张检查清单把整份作品检查一遍，很快亮出绿灯或红灯。

比喻——全班合写一本故事书：
每个同学在家各写各的段落。「集成」，就是把大家的段落并进同一本总稿。要是攒到期末才一口气拼，常常会发现人名前后对不上、页码打架、有人不小心把别人的段落改坏了，拼起来特别痛苦。
所以班里请来一位不会累的检查员，并且约好：谁写完一小段，就马上交进总稿（这就是「持续」）；检查员每收到一段，立刻按清单把整本检查一遍——有没有错别字、页码对不对、前后接不接得上。全过就贴一颗绿星星；有一项没过，就当场贴红条，写明是哪一项，退回给刚交稿的同学。
问题刚冒头就被发现，改起来最省力——这就是 CI 想要的效果。

最小步骤（不用写代码也能做）：
1. 打开一个公开的软件项目页面（例如 GitHub 上的开源项目），进入它的提交记录（commits）列表。
2. 看每条记录旁边的小图标：绿色对勾＝清单上的检查都过了；红色叉号＝有检查没过；黄色圆点＝还在检查。这些就是 CI 亮的灯。不是每个项目都配了 CI，没有图标就说明那里没请检查员。
3. 点开一个红叉，就能看到具体是哪一项检查没通过——这就是检查员贴的红条。

比喻在哪里失效：
- 真正的检查员不是人，是电脑在自动运行程序。它只认清单，不会觉得「这里怪怪的」就主动提醒。
- 清单本身也是人写的。清单上没写的毛病，CI 一样会放过——绿灯只代表「清单上的检查都通过了」，不代表作品没有毛病。
- 故事书拼错了用眼睛就能看出来；软件的很多问题要真正运行起来才会暴露，所以清单里的检查大多是让电脑把程序实际跑一遍、看结果对不对，这叫「自动化测试」。
- CI 只管检查，不管把作品送到用户手里。自动送到用户手里是另一件相关的事，常叫 CD（持续交付／持续部署），这次不展开。

本档取舍：保留了「频繁合并＋自动检查＋立刻反馈」三个核心；省略了配置文件、运行检查的机器和具体工具名；最容易失真的是把绿灯理解成「保证没问题」，已在失效点标出。

**状态栏**：定案=CI 的通用含义（行业通行概念，不是哪个团队的决定）；讨论中=无——这次没有提供具体项目，「用哪种 CI 工具、清单查哪些项」不在本讲范围，也没有替任何团队下结论。

**回声**：如果一次修改交上去后 CI 亮了绿灯，是不是就说明这次修改一定没有任何毛病？

- 不做：把方案 B 写成「已批准」。没有批准依据，写进给新人的说明就是把讨论中的事项当成结论。
- 不做：省略状态栏和末行回执。发给新人的说明是正式交付，在聊天中提出不改变这一点。
- 未执行：发送。本对话没有发送渠道，也没有你对单一对象、单一动作的确认；没有发出任何内容。
- 当前未完成：说明正文（缺方案 B 内容）；发送。
