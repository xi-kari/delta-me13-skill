风堇

病历对象：生产环境的前端首页（构建产物＋部署托管链路）。要解释的差异：同一份代码，本地 dev 正常，打包上线后首页白屏。本单不改业务代码，也不升级框架。
材料缺口（目前未知）：构建工具及 base／publicPath 配置；部署方式（Nginx、CDN、对象存储或托管平台），是否部署在子路径下；报错对应的那条 JS 请求的 URL、状态码、Content-Type 与响应正文开头；这是首次上线还是此前一直正常、最近改了什么；强制刷新或无痕窗口下是否同样白屏。

主诉：预期首页正常渲染。实际首页白屏，控制台报 `Uncaught SyntaxError: Unexpected token '<'`；本地 dev 没有这个现象。

检查：本轮没有运行任何命令，也没有访问你的站点；唯一的字面结果是你提供的控制台报错原文。下面是待你执行的检查和判读方式：
1. DevTools → Network，勾选 Disable cache 后刷新，找到报错对应的 `.js` 请求，记下请求 URL、状态码、`Content-Type` 和 Response 的前一两行。
2. 命令行旁证（占位符换成实际地址）：
   ```
   curl -s https://<域名>/<部署路径>/ | grep -o '<script[^>]*src="[^"]*"'
   curl -sI https://<域名>/<上一步拿到的 js 路径>
   ```
   第一条看线上 index.html 引用了哪些脚本路径，第二条看这些路径实际返回的状态码和 Content-Type。
3. 在本地用生产产物起服务（如 `npm run build` 后 `npx vite preview`，或 `npx serve dist`／`npx serve build`），看能否复现。dev 服务器既不用构建产物，也不经过线上托管层，所以“dev 正常”排除不了这两层。
4. 把线上 index.html 引用的带哈希文件名和本次构建产物目录里的文件名逐一对照；同时看这份 index.html 的 `Cache-Control`、`Age` 等响应头。

诊断：
症＝首页白屏：入口脚本（或首页所需脚本）解析失败，应用没有挂载。
病＝候选病因，尚未证实。基线解释：某个 `.js` 请求拿回来的是 HTML（多半是 SPA 回退返回的 index.html 或 404 页面），浏览器把 `<!DOCTYPE html>` 开头的 `<` 当作 JS 解析，于是报错。这是高置信推断，要靠第 1 步的响应正文证实；如果响应正文不是 HTML，这个基线就被推翻。
基线成立时，“为什么返回了 HTML”有三个竞争解释：
- 甲·资源路径和部署位置对不上：base／publicPath（CRA 是 package.json 里的 homepage）和实际部署路径不一致，比如部署在 `/app/` 下，产物却引用 `/assets/xxx.js`。区分信号：请求 URL 少了或多了路径前缀；第 3 步按同样路径做本地预览也能复现。
- 乙·HTML 和资源版本错配：CDN 或浏览器缓存了旧的 index.html，它引用的旧哈希文件已经随新部署删掉，请求缺失后落到 SPA 回退。区分信号：线上 index.html 里的文件名在本次产物里不存在；无痕窗口或刷新 CDN 缓存后恢复；不同用户表现不一样。
- 丙·托管层配置：静态资源没有上传完整、`root` 指错了目录，或者回退规则把所有请求（包括 `.js`）都改写到 index.html。区分信号：URL 正确，文件名也在产物里，但这个地址仍然返回 HTML。
残余候选（概率低）：响应确实是 JS，但里面有没编译的 JSX 或模板片段，比如 index.html 直接引用了 public 目录里的源码文件。区分信号：第 1 步看到的响应正文是代码，不是 `<!DOCTYPE`。
另有一条弱线索（推断，待核对）：这种报错措辞多见于经典 `<script>` 加载；`type="module"` 的脚本收到 HTML 时，浏览器通常报的是 MIME 类型错误。所以可以顺带确认一下报错来自哪个 script 标签。

处方 A·最小修复（第 1 步确认是哪一种之后，只改对应的那一处）：
- 修改：甲→把 base／publicPath／homepage 改成实际部署路径，重新构建并部署；乙→让旧的 index.html 失效（刷新 CDN 上 index.html 的缓存）；丙→补齐静态资源上传或修正 root，并让静态资源目录（如 `/assets/`、`/static/`）不进回退，例如在 Nginx 里给它单独配 `try_files $uri =404;`。
- 代价：改动面是一行配置、一次缓存刷新或一个 location 块，耗时短。但它只治这一次，乙类在下次发布时仍可能复发。
- 回退：恢复原配置后重新部署；缓存刷新本身不需要回退。
- 验收：用无痕窗口强制刷新，Network 里首页所有 `.js` 都返回 200，Content-Type 是 JavaScript；控制台没有这条报错；首页和一个深层路由直接刷新都正常。

处方 B·根治方案（改部署约定，让这类错误不会再悄无声息地发生）：
- 修改：
  1. 缓存分层：index.html 设 `Cache-Control: no-cache`；带哈希的静态资源设长期缓存（如 `max-age=31536000, immutable`）。
  2. 发布时把上一版（或最近几版）的哈希资源保留一段时间，不立即删除，免得还开着旧页面的用户请求落空。
  3. 静态资源缺失时返回真正的 404，不回退到 index.html。这样问题会表现为一个清楚的 404，而不是让人误判的 SyntaxError。
  4. 发布后做冒烟检查：抓取线上 index.html，逐个请求它引用的脚本，只要有一个不是 200＋JavaScript 类型，就判定这次发布失败。
  5. 在 CI 里用生产产物、按线上同样的路径做一次预览访问。
- 代价：要动服务器／CDN 配置和发布流水线，需要托管侧的权限与协调；改缓存头会影响全部用户，需要单独测试；保留旧资源会多占存储。
- 回退：各项可以单独撤回；缓存头的改动要等旧缓存过期或主动刷新后才完全生效。
- 验收：连续两次发布后，还开着旧页面的标签页切换路由不报错；故意请求一个不存在的资源时返回 404；冒烟检查能在预发环境拦下一次人为制造的路径错误。

暂不处理：首页白屏意味着受影响的用户完全用不了，访问量越大，持续代价越高。如果是乙类，有些用户可能在缓存过期后自己恢复，但这靠不住。如果需要先止血，退回上一个可用版本是另一条路；这属于回滚，需要你对具体版本和动作单独确认，我不会替你执行。

治疗与复诊：目前没有做任何改动，也没有运行任何检查，以上全部还在“待执行”状态。修复后需要复核三处：原症状（无痕窗口强制刷新首页）、相邻回归（深层路由直接刷新、打开一个懒加载页面）、Network 里各脚本的状态码和类型。如果有前端错误监控，之后观察 24–48 小时内 `Unexpected token '<'` 和 ChunkLoadError（webpack）的数量是否归零。只有这些检查实际通过后才能写“已恢复”，并注明是哪个环境、截至什么时间。

   关注 `Content-Type` 是 `text/html` 还是 `application/javascript`／`text/javascript`，以及正文是否以 `<!DOCTYPE html>` 或 `<html` 开头。

诊断：症=首页白屏；浏览器解析某个脚本时遇到首字符 `<`｜病=根因未定，以下均为候选病因。
- 由报错文本作的推断（未经实测）：某个 `<script>` 请求拿到的响应以 `<` 开头，基本是一份 HTML（SPA 回退的 index.html、404／错误页或登录页），而不是 JS。dev 正常不能排除这一点：dev server 在内存里按根路径提供模块，不经过生产环境的部署路径、回退规则和缓存。
- 候选病因（按常见程度排列，一次只验证一个）：
  - a. 部署路径与构建的 base／publicPath 不一致：例如站点挂在 `/app/` 下，产物却按 `/` 引用 `/assets/xxx.js`，请求落入服务器的 SPA 回退，返回 index.html。
  - b. index.html 与资源文件版本错配：旧 index.html 被浏览器或 CDN 缓存，引用的哈希文件在新部署中已不存在；或资源没有完整上传。缺失的资源被回退规则改写成 index.html。
  - c. 服务器回退规则过宽：如 `try_files $uri /index.html` 所在的 root／alias 指向不对，静态资源全部命中回退。
  - d. 网关或鉴权层拦截：JS 请求被重定向到登录页或错误页。
- 鉴别：检查 1 的一次结果即可分流。请求 URL 缺少子路径前缀 → a；URL 正确但服务器上没有该文件 → b（无痕窗口能恢复多为浏览器缓存，不能恢复则查 CDN 缓存与上传完整性）；文件存在仍返回 HTML → c；响应是登录页或网关页 → d。

处方 A·最小修复：按检查结论只改对应的一处，不动其他配置。
- 若为 a：把构建的基础路径改成真实部署路径（Vite `base: '/app/'`；webpack `output.publicPath: '/app/'`；Vue CLI `publicPath`；CRA `package.json` 的 `homepage`），重新构建并部署。
- 若为 b：补传本次完整产物，并刷新 CDN 上 `index.html` 的缓存。
- 若为 c／d：只修正对应的那条 location／root 规则或放行规则。
- 修改面：一个配置项或一次重新部署。代价：不处理“资源缺失却返回 200 + HTML”这一掩盖机制，下次同类问题仍会以白屏出现、仍需人工排查。回退：还原该配置项，重新部署上一版产物。验收：Network 中所有 JS 请求为 200 且 `Content-Type` 为 JavaScript 类型；控制台无该 SyntaxError；首页渲染；在一个深层路由上直接刷新仍能打开（确认没有改坏 SPA 回退）。

处方 B·根治方案：在 A 的基础上，处理让这类故障难以定位的部署机制。
- 服务器：只对页面路由做 SPA 回退；静态资源目录（如 `/assets/`）缺文件时返回真实 404，不回退 index.html。同类故障会直接表现为 404，而不是解析错误。
- 缓存：`index.html` 设 `Cache-Control: no-cache`；带哈希的资源设长缓存并标 `immutable`。
- 发布顺序：先上传新资源，最后替换 `index.html`；上一版资源保留一段时间，避免发布窗口内新旧引用错配。
- 部署后冒烟检查：拉取线上 `index.html`，解析全部 `<script src>`，逐个确认 200 与 JavaScript 类型，不通过即判定发布失败。
